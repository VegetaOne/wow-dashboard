# WoW Dashboard – Sprachumschalter (i18n)

> Stand: 2026-09-19 · **in Arbeit, etwa zur Hälfte fertig**
> Leitsprache ist Englisch: `en` definiert die Schlüssel, `de` muss sie vollständig
> bedienen — ein vergessener Eintrag ist ein Typfehler beim Bauen, kein leerer Text
> zur Laufzeit.

## Wie es gebaut ist

| Datei | Rolle |
| --- | --- |
| `src/lib/dict/<bereich>.ts` | Die Texte. Je Bereich eine Datei mit `export const en` und `export const de`. |
| `src/lib/dict/index.ts` | Führt die Bereiche zu `EN` / `DE` zusammen und leitet `TranslationKey` aus `EN` ab. |
| `src/lib/i18n.ts` | Mechanik: `translate`, `translator`, `classCode`, `formatRemaining`, `dateLocale`. **Darf nichts serverseitiges importieren** — landet im Browser-Bündel. |
| `src/lib/t.ts` | `getT()` für Server-Komponenten. Liest die Konfiguration, also Prisma — darum getrennt von `i18n.ts`. |
| `src/components/I18nProvider.tsx` | `useT()` und `useLanguage()` für Client-Komponenten. Das Wurzel-Layout liest die Sprache einmal auf dem Server und reicht sie hinein. |
| `src/lib/runtime.ts` | `locale()` leitet den `locale`-Parameter der Blizzard-Abfragen aus der Sprache ab. |

Die Sprache gilt für die **ganze Instanz**, nicht pro Nutzer, und steht in `AppConfig`.
Sie steuert zwei Dinge: die Oberflächentexte und die Sprache der Namen, die von der
API kommen (Gegenstände, Bosse, Fraktionen).

## Regeln

- **Schlüssel niemals doppelt über Bereiche hinweg** — beim Zusammenführen gewinnt sonst
  still der spätere Eintrag. Das Bereichspräfix (`equipment.`, `guild.`, …) hält sie
  auseinander, also bekommt jeder Schlüssel eines.
- **Kein fester Text in einer Komponente**, auch nicht als Fallback oder `aria-label`.
- **Platzhalter in geschweiften Klammern**: `"progress.modeProgress": "{difficulty}: {percent}%"`,
  aufgerufen als `t("progress.modeProgress", { difficulty, percent })`.
- **Keine Sätze aus Teilstücken zusammenkleben.** Ein Satz ist ein Schlüssel, sonst
  stimmt die Wortstellung in der einen Sprache nie.
- **Zahlen, Daten und Geld** über die gebundenen Formatierer: `useFormat()` in Client-,
  `getFormat()` in Server-Komponenten, dann `f.number(x)`, `f.date(ts)`, `f.money(c)`.
  Nie `toLocaleString()` ohne Locale, und nie eine Formatierungsfunktion ohne Sprache —
  ein Standardwert `"en"` wäre genau der stille Fehler, den `format.ts` verhindern soll.
- **Mengenangaben** über `tPlural("bereich.name", count)` mit den Schlüsselpaaren
  `.one` / `.other`. Kein `Intl.PluralRules`.
- Klassenkürzel stehen als eigene Tabelle in `i18n.ts`, nicht im Wörterbuch.

## Vorgehen je Bereich

Ein Bereich in einem Durchgang, nicht quer über alle:

1. Alle festen Strings der Komponenten dieses Bereichs sammeln, auch `title`, `alt`,
   `placeholder` und `aria-label`.
2. Sie als `en` in `src/lib/dict/<bereich>.ts` schreiben — englisch formuliert, mit
   Präfix, thematisch gruppiert und kommentiert.
3. `de` vollständig dazu. Der Typ `Record<keyof typeof en, string>` erzwingt es.
4. Komponenten umstellen: Server-Komponente `const t = await getT()`,
   Client-Komponente `const t = useT()`.
5. `npx tsc --noEmit` und `npm run build`.
6. **Gegenprobe:** in den geänderten Dateien darf kein Umlaut und kein deutsches Wort
   mehr in einem String-Literal stehen. `grep -nE '"[^"]*(ä|ö|ü|ß|Ä|Ö|Ü)[^"]*"'` über
   `src/components` findet die Reste.

## Offen

- **Deutsch heisst hier Schweizer Schreibweise** (`de-CH`, TT.MM.JJJJ) — bewusst so,
  weil die App für den Heimgebrauch gebaut ist.
- Die Sprache ist instanzweit. Ob sie später pro Nutzer gehört, ist nicht entschieden;
  `UserPreference` wäre der Ort dafür.
